# Lab plan: our characters in a fully 3D world

A temporary, self-contained experiment for the Labs page. It answers one question:

> Can our character system (rigs, animation, the mocap store, combat poses and their look) live in a real 3D world
> built with three.js and Rapier, with every piece of art made by code, while staying as easy for AI coding agents
> to work on as the animation system is?

It is a test, not a new engine. Nothing in `engine/` or `src/emberdeep/` changes. When the question is settled, the
lab, its vendored libraries and its Labs entry are deleted or promoted.

## Decisions (agreed)

| Topic | Decision |
|---|---|
| Renderer | three.js **r186** (`three@0.186.1`; r180 or later was the requirement). `WebGPURenderer` from `three/webgpu`, which falls back to WebGL 2 by itself when WebGPU is missing. One code path for both. |
| Physics | Rapier 3D, SIMD build: `@dimforge/rapier3d-simd-compat@0.21.0` (WebAssembly embedded in the JavaScript, so nothing is fetched at run time). |
| GPU rule | WebGPU never decides anything in gameplay. Gameplay (movement, physics, AI, combat) runs on the CPU at a fixed 60 Hz; the renderer only reads the state. Every visual feature must work on both backends. |
| Art | Everything made by code: geometry built in code, textures generated by code (our `E.tex` functions and others), no image, model or sound files. No 3D model imports. |
| Self-contained | All dependencies are vendored in the repository (no CDN, no network). |
| Performance | Not a concern for this test. |
| Fallback | If three.js or Rapier can't meet the rules above, a custom renderer or physics engine is acceptable (see *If three.js or Rapier fall short*). |

## Things to be clear about (trade-offs)

1. **The GPU rule is mostly automatic.** Rapier and our game code run on the CPU, so the renderer can't change
   gameplay by accident. In practice the rule means three things:
   - no WebGPU-only features (compute shaders, storage buffers);
   - materials written only in TSL, three.js's node shading language, which compiles to both WebGPU and WebGL 2;
   - nothing read back from the GPU into gameplay (no GPU picking, no GPU particles that hit things).

   The lab proves it: it runs the same 600 steps on both backends and shows a hash of the game state, which must
   match.
2. **SIMD needs a 2023-or-later browser.** WebAssembly SIMD runs in every current browser (Safari from 16.4). No
   non-SIMD fallback is planned; adding one later is a one-line package swap.
3. **Self-contained, but served, not double-clicked.** three.js ships as ES modules, which browsers won't load from a
   file opened straight off the disk. The lab is a folder (`examples/lab-3d/`) that works on the site and from any
   local web server (`npx serve`, `python3 -m http.server`). Our other labs are single files; bundling this one into a
   single file is possible later with a bundler, but not needed for the test.
4. **"All art by code" rules out the CC0 model kits.** Props, walls and floors are written as code (boxes, cylinders,
   lathes, extrusions, procedural textures), the way our props are today. Agents can write new ones; nobody imports
   files.
5. **Putting our characters in 3D has two answers, and the lab shows both side by side:**
   - **Card:** our engine draws the character exactly as it does now, from the camera's angle, into a picture on a
     camera-facing card in the 3D scene. The look is identical. The limits: a character is flat, at one depth (a
     sword can't swing behind a pillar), it looks like cardboard from straight above, and it is shaded by our tone
     ramps, not by the scene's lights.
   - **Puppet:** the same rig, driven by the same animation, but with real 3D parts (tapered limbs, head, hair, cape)
     hung on its joints. Our rig already computes every joint in 3D (`rig.J`, placed in the world by `rig._w`), so
     the motion is identical. The character becomes truly 3D: correct depth, real light and shadow, any camera. The
     look is an approximation of ours (toon shading in our colors, outlines, optional pixel-art pass), not our
     hand-tuned drawing.
6. **Readable for agents means two rules.** Agents never read the vendored libraries (several MB of minified code);
   they read the lab's own small files. The known risk is that agents write older three.js code (`WebGLRenderer`,
   `ShaderMaterial`, `EffectComposer`, `onBeforeCompile`) that doesn't work with `WebGPURenderer`. A check fails on
   those APIs, as Riftlight does.
7. **Cameras.** Fixed presets match our five views (isometric, three-quarter, top-down, brawler, side). Our views
   stretch height slightly (the "boost"); a custom projection matrix reproduces that exactly. Because this world
   has perspective, the lab can also offer a free-floating camera, first person and a third-person chase camera.
   Those come free with real 3D, so they're included even though we decided we could live without them.

## What the lab contains

### The room
- Four walls, four pillars, a floor, built from an ASCII map with heights (`#` wall, `P` pillar, digits for raised
  floor), so an agent can edit the level as text.
- Boxes in the middle: a stack and a few loose ones, real Rapier bodies that the hero can push and topple.
- Procedural materials: flagstone floor and brick walls generated by `E.tex` into textures (nearest filtering, so
  texels stay crisp), wood for the boxes, stone for the pillars.
- Light: a sun with real shadows, two torches (point lights, flicker), an ambient fill.

### Characters
- **The hero walking a lap round the pillars**, as in the free camera room, with an option to take control (WASD,
  attack, dash).
- **A switch between Card and Puppet** for every character, and a side-by-side mode that shows both at once.
- **A mocap clip** from the store playing on a second figure (the hero set's idle and walk, and one CMU take), to show
  that the store drives both modes unchanged.
- **Dan**, our custom rig, to show that a non-human body works too.
- **An attack swing** with its weapon trail, to show the combat poses and where each mode draws effects.

### Cameras
- Fixed: the five engine views, with rotation in 45° steps.
- Free orbit: drag to turn and tilt, wheel to zoom.
- Free fly (first person) and a third-person chase camera.
- Fix camera: freezes the view and puts it in the address (`?cam=`), like the free camera room.

### Look
- Full resolution, or a pixel-art pass (the scene drawn at 270 lines and enlarged with whole pixels).
- Outlines found from depth and normals, toon bands, distance fog: each a toggle.

### Proof and tools
- The backend in use (WebGPU or WebGL 2), `?backend=webgl` to force the fallback, and the game-state hash after a
  fixed run on each.
- `window.__lab3d`: `step(n)` advances exactly n fixed steps, `state()` returns positions and the hash,
  `setCamera(...)`, `capture()` returns the frame. Tests and agents drive the lab through it.
- An info panel per section: what it shows, what to try, what carried over from our engine and what didn't.

## How it's built

```
vendor/three-0.186.1/        three.webgpu.js, three.tsl.js, LICENSE (MIT), VERSION
vendor/rapier3d-simd-compat-0.21.0/   rapier.mjs, LICENSE (Apache-2.0), VERSION
tools/vendor-3d.mjs          fetches exact versions once with npm pack, copies the files, records sizes and checksums
src/lab3d/
  lab3d.template.html        page, panel, import map (local paths only)
  00-world.js                ASCII map -> wall, pillar and floor meshes; Rapier colliders from the same map
  10-materials.js            procedural textures (E.tex) and TSL materials; the banned-API list lives in the check
  20-physics.js              Rapier world, fixed 60 Hz step, character controller, boxes; state hash
  30-characters.js           rig update (our engine), Card mode (canvas texture on a card), Puppet mode (parts on rig.J)
  40-cameras.js              fixed presets (with the boost), orbit, fly, chase, fix
  50-look.js                 pixel-art pass, outlines, toon, fog
  60-panel.js                controls, info cards, window.__lab3d
tools/lab3d-test.mjs         opens the lab on the WebGL 2 fallback (and WebGPU where the machine has it), steps it,
                             compares hashes, checks for errors, writes screenshots; runs the banned-API check
```

- `tools/build.mjs` copies the folder to `examples/lab-3d/`; `vercel.json` serves it at `/lab-3d`; `src/labs.json`
  lists it under Temporary with the date and the question.
- Our engine (`engine/my-3d2dge.js`) is loaded as is, for the rigs, the animation, the mocap store and the textures.
  The lab only reads from it.
- Every lab file opens with a header that explains it, in the style of the agent edition: an agent reads the headers
  and nothing else to make a change.

## Milestones

1. **Skeleton:** vendor the libraries, renderer with the fallback, the room from the ASCII map, the fixed and free
   cameras, the backend label.
2. **Physics:** the Rapier world, colliders from the map, boxes, the character controller, the fixed step and the
   state hash on both backends.
3. **Card characters:** the hero's lap, player control, the attack, the mocap figure, Dan.
4. **Puppet characters:** parts on the rig's joints, toon materials in our colors, the side-by-side view.
5. **Look and finish:** pixel-art pass, outlines, fog, info cards, `window.__lab3d`, the test script, the Labs
   entry.

Rough effort: 3-5 focused sessions. Each milestone ends with screenshots on both backends.

## How we'll judge it

- **Look:** Card and Puppet next to the engine's own drawing at the same camera. Does either keep what we love?
- **Feel:** the hero under player control, swinging and pushing boxes. Does it still feel like ours?
- **Agents:** hand the lab to a fresh agent with a small task (add a prop, a new room layout, a second enemy) and see
  how far it gets from the headers alone.
- **The rule holds:** identical state hashes on WebGPU and WebGL 2.
- **Cost:** how much code the lab needed beyond the vendored libraries, as a preview of what a real engine would
  carry.

## If three.js or Rapier fall short

- **three.js:** if a needed effect can't be done in TSL for both backends, try a simpler look first. If the
  renderer itself blocks us, the fallback is our own small renderer (fly mode in the free camera room is a working
  start: a depth buffer, perspective-correct textures, clipping), with WebGL 2 for speed.
- **Rapier:** if the character controller fights our combat feel (snappy starts and stops, hit-stop, knockback),
  move the hero with our own kinematic code and keep Rapier for the boxes. Our engine's collision is already
  enough for walking among walls and pillars.

## Out of scope

Emberdeep, the engine files, the agent edition, importing model files, sound, performance work, and phones (the
lab should work on them, but that isn't tested).
